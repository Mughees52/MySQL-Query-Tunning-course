Reading big plans

Cost of a node ≈ actual time × loops

Scary flags aren't automatically the problem. Multiply, then judge.

-> Sort: rev DESC, limit 10  (actual time=1348 rows=10) ← "Using filesort"… of 30 rows
-> Aggregate using temporary table  (actual time=1345 rows=30)
-> Nested loop inner join  (actual …1214 rows=1.03e6)
-> Index lookup on o (status='completed')  (actual …436 rows=1.03e6)
-> Single-row PK lookup on c  (actual 0.7 µs … loops=1.03e6)
0.7 µs × 1,030,000 loops ≈ 0.7 s — the innocent-looking line is the bill

Lesson 4.6

When do you stop?

Requirement: < 2 s. You're at 1.14 s. Two more optimizations would buy ~0.4 s — one adds a four-column index, the other a join hint. Take them?
No — ship it. Each further change adds write cost, fragility, and review surface for latency nobody asked for. Write both ideas in the ticket for the day the requirement tightens. Tuning without a stop condition is how databases accumulate 40 indexes and 200 hints nobody dares remove.
caveat: requirements are distributions — a fine p50 with a terrible p99 is a different conversation
Course wrap-up

Your tuning checklist

Find the target
slow log + sys.statement_analysis · pick by frequency × duration · smell: rows examined ≫ rows sent
Measure honestly
warm cache, run twice, write it down, save the result set · EXPLAIN ANALYZE, not vibes
Access paths first
seeks not scans · bare columns in predicates · equality→range composite order · covering for the hot few · retire redundant indexes invisible-first
Then shape
filter early, project late · right grain before aggregating · IN not cross-column OR · NOT EXISTS not NOT IN · LEFT-join filters in ON
Then the optimizer's worldview
est vs actual gaps · histograms on skewed filter columns · hints as documented, dated, last-resort bets
Then architecture
keyset pagination · summary tables and denormalized totals when query tuning has done its job · stop at the requirement
