InnoDB's one big idea

Tree descent vs. table sweep

The clustered index stores the whole table sorted by primary key.

WHERE id = 42

primary key → descend the B+tree
3 page reads → the row. ~free.

WHERE customer_id = 137

no index → check every row
1.2M rows examined → 243 kept. 110 ms.
the full table scan is the villain of chapter 1

Finding what to fix

Rows examined ≫ rows sent

The single best smell test in MySQL — in the slow log and in sys.statement_analysis.

rows examined
9,000,000
rows joined
2,580,000
rows sent
12
The morning revenue report does 750,000× more work than its output justifies.
An index or a rewrite is hiding in that gap.
pick targets by frequency × duration — not the single slowest query
Before you measure anything

Three rules, or your numbers are noise

01
Warm up first
First run may be paying disk-to-buffer-pool tax. Run twice; time the later runs.
02
Change one thing at a time
An index or a rewrite between measurements — never both. Otherwise which one helped?
03
Keep a scorecard
Query, plan summary, milliseconds, date. "It feels faster" has shipped a lot of regressions.
