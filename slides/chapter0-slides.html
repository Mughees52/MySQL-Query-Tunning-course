Before anything else

How MySQL reads your SELECT

You write it top-to-bottom. MySQL executes it in a different order — and most surprises in SQL trace back to not knowing which.

as written
5SELECT ship_country, COUNT(*) AS orders
1FROM orders
2WHERE status = 'completed'
3GROUP BY ship_country
4HAVING COUNT(*) > 50000
6ORDER BY orders DESC
7LIMIT 3;
as executed — rows surviving each stage (measured on UrbanCart, not derivable from the query)
1FROMgather the raw rows1,200,000
2WHEREfilter first — the SELECT alias doesn't exist yet1,032,479
3GROUP BYbucket what survived, per ship_country17 groups
4HAVINGWHERE for groups — it can see COUNT(*)7
5SELECTproject the columns — the alias orders is born here7
·DISTINCTwould run here — and be a no-op: GROUP BY already left one row per country—
6ORDER BYsort — running after SELECT, it CAN use the alias7
7LIMITkeep the top slice: US · GB · DE3
the consequence: WHERE orders > 50000 → ERROR 1054, unknown column — WHERE runs at step 2, the alias is born at step 5
ORDER BY orders works fine — it runs at step 6 · chapter 3 turns this pipeline into a tuning tool
1,200,000 → 1,032,479 → 17 → 7 → 3 · every count measured live · the earlier a row dies, the less everything after it costs

The dialect gap

MySQL has no FULL OUTER JOIN

Keep both sides' exclusives? PostgreSQL writes one keyword. MySQL composes it:

countries LEFT JOIN ship_stats …arm 1 — everything from the left, matches attached (17 matched + 15 left-only)
UNION ALL
ship_stats LEFT JOIN countries … WHERE co.code IS NULLarm 2 — right side's exclusives only, via the anti-join (0 here — every ship code is in the lookup)
= 32 rows, both sides completeUNION ALL, not UNION: the arms can't overlap, so dedup would be paid for nothing
arm 2 doubles as a data-quality probe: rogue codes surface there · measured in lab 0.3
A query inside a query

Subqueries: three positions, three meanings

in SELECT — one value per row
SELECT ship_country, AVG(total_cents),
  (SELECT AVG(total_cents) FROM orders)
FROM orders GROUP BY ship_country;
plan: "subquery in projection; run only once"
must return a single value · uncorrelated = executed once, reused
in WHERE — a dynamic filter
SELECT COUNT(*) FROM orders
WHERE total_cents >
  (SELECT AVG(total_cents) FROM orders);
543,009 rows · "run only once"
threshold computed at run time — no stale magic numbers · IN (SELECT…) → semijoin (deep dive 3.15)
in FROM — a derived table
SELECT … FROM
  (SELECT … GROUP BY …) AS t
JOIN … ;
merged or materialized (deep dive 3.16)
results acting as a table · readable once — inside-out beyond one level → use a CTE
correlated subqueries run per row: 1 µs on an index = fine (3.13) · 460 ms per group = the capstone's villain
WITH — the readable building block

Common table expressions

WITH country_rev AS (
  SELECT ship_country, COUNT(*) AS orders, SUM(total_cents) AS rev
  FROM orders WHERE status = 'completed'
  GROUP BY ship_country)  ← the block, stated first, named
SELECT co.region, SUM(cr.orders), ROUND(SUM(cr.rev)/100, 2)
FROM country_rev cr
JOIN countries co ON co.country_code = cr.ship_country
GROUP BY co.region ORDER BY 3 DESC;  ← reads like a sentence
measured: ~0.5 s — identical plan to the FROM-subquery version
referenced twice? materialized once — 0.51 s vs 0.96 s inline (lab 3.14)
the capstone's step 4 is this exact shape replacing 17 correlated subqueries
WITH costs nothing; its job is top-to-bottom readability — and same-statement reuse for free

Views store queries. Temp tables store data.

Materialize the view — and mind the trap

v_order_geo (3-table join view), measured:
query through the view: 1.6 s — every single time
materialize once (2.5 s) → then 0.18 s · 0.21 s · …
break-even at the 2nd query · ~8× on every one after
SELECT … FROM tmp_de a JOIN tmp_de b ON …;
ERROR 1137 (HY000): Can't reopen table: 'a'
a CREATE TEMPORARY TABLE table cannot appear twice in one statement
(PostgreSQL allows it — classic porting trap) · fix: two copies, or a CTE
the choice: view = always fresh, recomputed on every read · temp table = a snapshot you refresh on your schedule
dashboards hitting the same slice repeatedly → materialize · one-off audit questions → query the view
